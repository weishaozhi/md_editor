## 复杂问题与解决方式

### 1. `*` 与 credentials 的浏览器规范

按 W3C Fetch 规范，`Access-Control-Allow-Origin: *` 与 `credentials: include` 不能同时出现。旧代码两者都开 → 上线后所有带 cookie 的请求失败。

**解决**：启动校验是首选防线（生产 fail-fast），运行时检测太晚（要等浏览器报错）。Debug 模式允许 `*` 但代码层强制 credentials=False，避免不安全组合在任何环境下出现。

### 2. Pydantic 配置项类型选择

考虑过用 `list[str]` 直接解析（`CORS_ALLOW_ORIGINS: list[str]`），但 Pydantic 对 list 的 env 解析要求 JSON 语法，运维成本高。最终用 `str` + 启动时切分，启动校验逻辑更清晰。

### 3. 默认值给本地端口还是空

如果默认空值，启动后任何请求都跨域失败，开发者必须先配 `.env` 才能跑——摩擦太大。默认给 `http://localhost:5173,http://localhost:3000`（Vite + CRA 默认端口），开箱即用；上线必须改 `.env`。

### 4. 测试用例的进程隔离

不能在当前 Python 进程直接改 `settings` 后断言——pydantic-settings 在 import 时就锁定。改用 `subprocess.run` 启动独立 Python 进程，按需设置 `CORS_ALLOW_ORIGINS` 和 `DEBUG` 环境变量，再 import 验证。4 个用例互不污染。

## 验证方式与结果

- `backend/test/08_cors/test_cors_config.py` — 4/4 PASS（退出码 0）
  - `* + DEBUG=False` → 退出码 1，`RuntimeError: CORS_ALLOW_ORIGINS='*' 不能在生产环境使用`
  - `* + DEBUG=True` → 退出码 0，origins=`['*']`，credentials=False
  - `https://a.com,https://b.com + DEBUG=False` → 退出码 0，origins 与 credentials=True
  - 空字符串 → 退出码 1，`RuntimeError: CORS_ALLOW_ORIGINS 为空`
- `python -c "from app.main import app; print(app.version)"` — 打印 `1.1.0`，默认 origins 与 localhost 一致

## 安全建议

1. **不要**把 `.env` 提交到仓库（已通过 `.gitignore` 第 19 行 + 第 49 行排除；只提交 `.env.example`）
2. **不要**在生产环境的 `.env` 里保留 `SECRET_KEY=replace-me-...` 占位符；用 `python -c "import secrets; print(secrets.token_urlsafe(48))"` 生成
3. **不要**在生产 `.env` 里把 `DEBUG` 设为 `True` —— 启动校验允许 `*`，会触发不安全的 `*` 模式（虽然代码层强制 credentials=False）
4. CORS allowlist 上线前必须替换为实际域名，例如 `https://md.your.domain,https://admin.your.domain`
5. CORS allowlist 加新域前必须经过评审；避免通配子域（`*.your.domain` 在 CORS 中无效，浏览器不接受）
6. 后续如果新增任何 webhook / 回调接口，请单独评审是否需要新增到 allowlist
