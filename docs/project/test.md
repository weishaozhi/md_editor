# MD Editor · 测试规范（test.md）

> 本文档是测试策略与目录结构的说明；具体手工 / 端到端脚本索引请参考 [`../TESTS.md`](../TESTS.md)。

---

## 1. 测试目标

1. **回归保护**：核心功能有最小可重复的断言。
2. **快速定位**：报错时能定位到具体场景与脚本。
3. **可读报告**：人工一眼看出哪些场景通过、哪些失败、最近一次运行结果如何。

---

## 2. 目录与命名

```
backend/test/
├── NN_<topic>/                  # 两位序号 + 主题名；按主题归档
│   ├── test_<scenario>.py       # 每个脚本只覆盖一个明确场景
│   └── README.md                # 选填：脚本内补充说明
```

- **主题序号**：两位数字，从 `01` 开始；新增主题取下一个空号，不要插入中间。
- **脚本命名**：`test_<动词>_<对象>.py`；尽量保持小写 + 下划线。
- **不要**在脚本里掺杂与主题无关的断言；新增场景应拆为新脚本。

---

## 3. 测试层级

| 层级 | 适用 | 工具 | 输出 |
|---|---|---|---|
| 单元 | 纯函数 / 算法（如 `formatDate`、`buildRemovedRows`、同步滚动比例） | `assert` 即可；可选 `pytest` | PASS/FAIL 计数 + 退出码 |
| 端到端（HTTP） | 接口契约 / 业务链路（注册→登录→编辑→版本） | `urllib` / `httpx` + `assert` | 退出码 0/1/2 |
| 半自动 E2E | 启停脚本、浏览器交互（Playwright 后续） | 手工触发 + 脚本断言 | 退出码 0/1 |
| 跨层契约 | React Query key 一致性、schema 一致性 | Python 模拟前端哈希 | 退出码 0/1 |

> **CI 阶段**：建议把“单元 + 端到端 HTTP” 纳入 PR 必跑项；“半自动 E2E” 仅做 nightly。

---

## 4. 退出码约定

| 退出码 | 含义 |
|---|---|
| 0 | 全部断言通过 |
| 1 | 至少一个 `[FAIL]`（单元 / 数学）或 `AssertionError`（端到端） |
| 2 | 脚本自身异常（非断言错误） |

> 测试运行器只需看退出码即可判定通过/失败。

---

## 5. 编写规范

1. **每个脚本顶部**必须打印三行：
   - `BASE_URL`：直连后端 / 走 Vite 代理 / 无；
   - `前置条件`：服务是否已启、端口、是否需要清库；
   - `覆盖场景`：用编号列出。
2. **断言失败**要打印：
   - 期望值、实际值、关键参数（id、token、payload 摘要）。
3. **不打印敏感信息**：token、密码、邮箱可打印长度，但禁止打印原文。
4. **幂等性**：脚本应在每次运行后自清理（删新建用户 / 文件 / 版本）；或使用时间戳避免冲突。
5. **副作用声明**：脚本如会真实停止服务（`stop.bat`），必须在脚本头标注。

## 7. 写一个新测试的流程

1. 确认主题是否已存在；不存在则新增 `NN_<topic>/`。
2. 写脚本，遵循 § 5 的编写规范。
3. 手动运行一次，确认退出码符合 § 4。
4. 更新：
   - [`../TESTS.md`](../TESTS.md) 的目录结构 + 索引小节；
   - 本文档 § 6 通过率表；
   - 若属于某个修复 / 功能：在 [`../MAINTENANCE.md`](../MAINTENANCE.md) 或 [`project_state.md`](./project_state.md) 中挂一条引用。
5. 在提交信息里明确写出“新增测试 …（退出码 X / N 项断言）”。

---

## 8. 报错应对（与 [`project-bootstrap.md` § 3](./project-bootstrap.md) 对齐）

- 测试失败时，**先**确认是该脚本应被期望失败的旧行为，还是真实回归。
- 若是真实回归：先在 `project_state.md` 新建 ISS 条目，再去修复；禁止直接改脚本让断言“过”。
- 若是断言写错：在脚本同 PR 内修正，并写明“为什么这条断言之前写错了 / 现在应为什么”。
