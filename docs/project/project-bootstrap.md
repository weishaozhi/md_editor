## 2. 项目启动六大步骤

### 2.1 定需求（→ [`prd.md`](./prd.md)）
- **你必须**：拆出核心功能与非核心功能，写清用户流程、页面清单、完成度。
- **你必须**：对每个核心场景给出可验收的标准（如“登录成功 → 跳转 /；失败 → 提示且不锁账号”）。
- **你必须**：与用户一起确认视觉风格（简约 / 商务 / 参考站），导航栏样式、整体调性。
- **你不应**：在需求未稳定时直接进入实现。

### 2.2 定项目边界（→ [`prd.md#非功能需求`](./prd.md#非功能需求)）
- 至少明确四个维度：**安全 / 性能 / 可用性 / 成本**。
- 需要回答：是否对外上线？是否涉及用户隐私数据 / 支付？性能预算（如 P95、首屏、并发）是多少？

### 2.3 维护文档
- 项目启动期必须建立并持续维护：
  - `prd.md`：需求基线
  - `arch.md`：架构基线
  - `project_state.md`：状态/已知问题/下一步
  - [`README.md`](../../README.md)：项目入口
- `project_state.md` 的“已知问题”条目必须包含：**问题 / 现象 / 根因 / 解决方式** 四段。

### 2.4 开发规范 + 参考资料（→ [`test.md`](./test.md) + [`git-usage.md`](./git-usage.md)）
- 与团队讨论后决定是否落地：命名规则、文件大小上限、代码风格（如 Python PEP8、TS ESLint）。
- 必要时引入团队认可的**组件/表单/弹窗参考实现**（避免每次重新设计）。
- 测试规范：
  - 必须有测试目录，统一规划（参见 `test.md`）。
  - 单元测试必须存在并记录**通过率**、**最近运行结果**。
  - **后端日志必须打印**（INFO 起步，关键路径 WARNING/ERROR），日志格式与归档位置由后端决定。

### 2.5 接入 Git（→ [`git-usage.md`](./git-usage.md)）
- **项目开工前必须先接入 Git**，而不是写到一半再补救。
- 分支模型：至少覆盖 `release` / `pre` / `test`，并写明生命周期。
- 提交命名：`类型YYYY_MM_DD_HH_MM_简述`（例：`feature2026_07_29_11_55_visible`）。
- 提交类型：`feature` / `bugfix` / `refactor` / `docs` / `test` / `chore`。
- 一次提交只针对**一个** feature 或一个 bug；多要点要分行写清。
- 版本发布：
  - 每累计 **10 次提交** → 发布小版本 `vX.Y`。
  - 重要改动或新核心功能 → 发布主版本 `vX.0`。

### 2.6 其他重要规范
| # | 规范 | 关键约束 |
|---|---|---|
| 1 | 修改边界 | 只改本次任务相关的文件；不重构、不动 UI 风格、不改无关逻辑；不得不动时要先与用户确认，并记录在 `project_state.md` |
| 2 | 人的职责 | 人负责边界确认与质量验收 |
| 3 | 框架与模块划分 | 关键节点（架构设计、模块拆分）由人介入，AI 提供方案但不能自行决断 |
| 4 | 迭代节奏 | 小步迭代：先搭框架，再补各功能；每完成一个功能即验证一个 |
| 5 | API Key 安全 | API Key **不进前端、不进仓库**；通过环境变量 + 服务端调用；服务端必须鉴权授权后再代理 |
| 6 | 报错应对 | 提出报错前必须**新增证据**，否则停止；具体证据要求见下文 |
| 7 | 交叉验证 | 重要修复或结论必须做交叉验证（再跑一遍测试 / 多浏览器 / 多账号） |
| 8 | 复用沉淀 | 解决较复杂问题或产出可复用脚本时，最终验证后**记录并总结**到对应 `docs/` 文档 |
| 9 | **删除文件必须许可** | 删除任何文件（包括 `update/` 文件夹中的日志）前必须获得用户明确许可；不得自行决定删除 |
| 10 | 更新日志 | 每次改动确认完成后，在项目根目录 `update/` 文件夹生成 md 文件（命名：`YYYY-MM-DD_HH-mm.md`），包含：改动目的、时间、文件列表、复杂问题与解决方式、验证方式与结果、安全建议、Git 提交信息。确认无误后再执行 git commit |

## 3. 报错应对流程（科学应对）

> **原则：没有新增证据，就不要把同一个报错再发一次。**

当一个问题反复出现、或者现有修复不奏效时，按下列顺序补齐证据，再回到对话：

1. **最小复现**：用最小数据集 / 最短路径复现问题，记录复现命令与输入。
2. **加观测**：补充日志、断点、`console.log`、关键变量与分支打印，让问题可见。
3. **写小测试**：用一个单元测试或一段最小代码**锁住**能稳定复现该 bug 的行为（失败 → 通过 即修复证据）。

完成后请按以下模板更新 `project_state.md` 的“已知问题”条目：

```
**问题**：…
**现象**：…
**根因**：…
**证据**：最小复现 / 新增日志 / 锁定测试（任选其一或多项）
**解决方式**：…
```

## 4. 修改边界与人工介入点（速查）

| 触发点 | 必须人工确认 | 备注 |
|---|---|---|
| 涉及架构调整、新增模块、改动模块边界 | ✅ | AI 只出方案 |
| 涉及样式/UI 风格改动 | ✅ | 与本次任务无关的样式**不动** |
| 涉及数据库结构 / 接口契约变更 | ✅ | 同步更新 `docs/API.md` |
| 涉及删除或合并已有功能 | ✅ | 必须明确告知用户 |
| 涉及 API Key、密钥、token、用户隐私数据 | ✅ | 必须采用服务端代理 + 环境变量 |
| 单次提交跨多个 feature / bug | ❌（禁止） | 拆提交 |
| 改动后未跑相关测试即提交 | ❌（禁止） | 至少保证新增/受影响测试通过 |
| 在未提供证据的情况下反复报告同一报错 | ❌（禁止） | 按第 3 节补证据 |
| 未经许可删除任何文件 | ❌（禁止） | 包括 update/ 日志；删除前必须获用户许可 |

## 5. 文档维护约定

- **单一事实来源**：规范条目只写在专题文档；本入口只保留摘要与链接。
- **改动后回链**：修改任意专题文档后，回写本入口的对应小节，让入口保持“最新可达”。
- **状态每周清理**：`project_state.md` 的“下一步”条目必须每周复核，过期项迁移到“已完成”或删除。
- **测试同步**：新增/删除测试必须同时更新 `test.md` 与 `docs/TESTS.md`（若属于手工脚本）。
- **Git 同步**：版本号变更、发布分支调整必须同步到 `git-usage.md` 与本入口。
